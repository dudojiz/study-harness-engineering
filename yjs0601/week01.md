#강력한 모델도 실행 신뢰성을 보장하지 않는다.

핵심 용어 
역량 격차(Capability Gap): 벤치마크 성능과 실제 작업 성능 사이의 큰 간극.
하네스(Harness) : 모델 외부의 모든 것 -- 지시사항, 도구, 환경, 상태(state)관리, 검증(verification)피드백.
하네스 유발 실패(Harness-Induced Failure): 모델은 충분한 역량을 갖췄지만 실행 환경에 구조적 결함이 있는 경우. 
검증 격차(Verification Gap): 에이전트가 자신의 산출물(deliverable)에 대해 갖는 자신감과 실제 정확성 사이의 간극.
진단 루프(Diagnostic Loop): 실행 → 실패 관찰 → 특정 하네스 레이어에 귀속 → 해당 레이어 수정 → 재실행. 
완료 기준(Definition of Done): 기계 검증 가능한 조건들의 집합 — 테스트 통과, 린트 클린, 타입 검사 통과.

<실패하면 먼저 하네스를 점검>
핵심 원칙: 실패가 발생하면 먼저 모델을 교체하지 말고 하네스를 점검. 같은 모델이 비슷하게 잘 구성된 작업에서 성공한다면, 하네스 문제라고 가정.

모든 실패를 특정 레이어에 귀속.
-작업이 불명확했는가?
-컨텍스트(context)가 불충분했는가?
-검증 방법이 없었는가?
(작업 명세, 컨테스트 제공, 실행환경, 검증 피드백, 상태관리) 중 하나에 매핑.

### Chapter 2
#하네스란 실제로 무엇인가

OpenAI는 핵심 원칙을 "저장소(repo)가 명세(spec)다"로 정의
필요한 모든 컨텍스트는 저장소에 있어야 하며, 구조화된 지시 파일, 명시적 검증(verification) 명령어, 명확한 디렉터리 구성을 통해 전달되어야 한다.
-----------------------
Anthropic의 장기 실행 에이전트 문서는 상태(state) 지속성, 명시적 복구 경로, 구조화된 진행 추적을 강조.
----------------------
<핵심 개념>
- 하네스(harness)란 무엇인가: 모델 가중치 외부의 엔지니어링 인프라 전체.
- 지도를 줘라, 매뉴얼이 아니라 : OpenAI의 경험 AGENTS.md는 백과사전이 아니라 디렉터리 페이지여야 함. 100줄 정도가 적당.
- 제약하되, 마이크로매니지하지 마라.
- 컴포넌트를 하나씩 제거하라.

<5개 하위 시스템 하네스 모델>
지시 하위 시스템(레시피 선반): - 프로젝트 개요와 목적(한 문장)
                        - 기술 스택과 버전(Python 3.11,FASTAPI 0.100...)
                        - 첫 실행 명령어
                        - HARD 제약

도구 하위 시스템(칼 렉): 에이전트가 충분한 도구 접근권을 갖도록. 
                    보안을 위해 셸을 비활성화 하지 말것, 그렇다고 모든 것을 열어두지도 말것.-최소 권한 원칙

환경 하위 시스템: 환경을 자기 설명 상태로 만들 것. pyproject.toml 또는 패키지를 사용. 환경을 재현 가능하게 만들기 위해 docker 또는 개발 컨테이너.

상태(state) 하위 시스템(준비스테이션) : 장시간 작업에는 진행 추적이 필요. 간단한 progress.md.파일을 사용하여 기록.
                                완료된 것, 진행 중인 것, 차단된 것. 매 세션 종료 전에 업데이트하고, 다음 세션
                                시작 시 읽을 것.

피드백 하위 시스템(품질 확인 창): 투자 대비 효과가 가장 높은 하위 시스템. 
                        검증 명령어:   - 테스트: pytest tests/ -x
                                    - 타입 검사: mypy src/ --strict
                                    - 린트: ruff check src/
                                    - 전체 검증: make check (위 모두 포함)

<핵심 정리>
- 하네스 = 지시 + 도구 + 환경 + 상태(state) + 피드백. 다섯 가지 하위 시스템, 주방의 다섯 가지 기능 구역
- 모델 가중치가 아니면 모두 하네스. 하네스가 모델 역량이 얼마나 발휘되는지를 결정한다.
- 같은 모델에서의 컴포넌트 제거 실험은 한계 기여도 정량화에 사용할 것. 


### Chapter 3
#저장소를 단일 진실 공급원으로 만들것.
<지도에 무엇이 있어야 하는가>
OpenAI : 저장소에 없는 정보는 에이전트에게 존재하지 않는다.
"결정 정보를 올바른 장소에 두는 것"에 관한 것. 
src/api/ 디렉터리의 50줄짜리 ARCHITECTURE.md는 아무도 유지보수하지 않는 Confluence의 500페이지 설계 문서보다 만 배 유용.
<핵심 개념>
- 지식 가시성 격차 : 저장소에 없는 전체 프로젝트 지식의 비율. 격차가 클수록 에이전트의 실패율이 높다. 
                 이 프로젝트에 대해 얼마나 많은 암묵적 지식이 머릿속에 있는지, 그 중 얼마나 저장소에 들어갔는지 확인할 것.
 
- 시스템 오브 레코드(SoR, System of Record): 프로젝트 결정, 아키텍처 제약, 실행 상태, 검증 기준에 대한 권위 있는 출처로서의 코드 저장소.

- 콜드 스타트 테스트(Cold-Start Test): 위의 다섯 가지 질문. 몇 개나 답할 수 있는가가 지도가 얼마나 완전한가를 나타냄.
- 지식 부패율(Knowledge Decay Rate): 단위 시간당 낡아지는 지식 항목의 비율. 문서가 코드와 동기화되지 않는 것이 가장 큰 적.
- ACID 유추: 데이터베이스 트랜잭션 원칙(원자성, 일관성, 격리성, 내구성)을 에이전트 상태 관리에 적용하는 것. 

<좋은 지도를 그리는 방법>
1. 지식은 코드 옆에 있어야 한다. -> API 엔드포인트 인증에 관한 규칙은 API 코드 옆에 있어야 한다.
2. 표준화된 진입 파일을 사용할 것.-> AGENTS.md(또는 CLAUDE.md)는 에이전트의 "랜딩 페이지"입니다. 모든 정보를 담을 필요는 없지만 에이전트가 세 가지 질문에 빠르게 답할 수 있도록 해야 합니다: "이 프로젝트가 무엇인가", "어떻게 실행하는가", "어떻게 검증하는가". 50-100줄이면 충분.
3. 최소화 하되 모든 지식은 명확한 사용 사례가 있어야 함.-> 규칙을 제거해도 에이전트의 결정 품질에 영향을 주지 않는다면 그 규칙은 존재하지 않아야 함.

4. 코드와 함께 업데이트 할 것.
   가장 간단한 방법 : 아키텍처 문서를 해당 모듈 디렉터리에 둘 것. 

ACID 원칙으로 에이전트 상태 관리하기.
- 원자성(Atomicity): 각 "논리적 작업"(예: "새 엔드포인트 추가 및 테스트 업데이트")은 하나의 git 커밋을 받는다.
- 일관성(Consistency): "일관된 상태" 검증 조건을 정의하십시오 — 모든 테스트 통과, 린트 오류 없음. 에이전트는 각 작업 후 검증을 실행.
- 격리성(Isolation): 여러 에이전트가 동시에 작업할 때 상태 파일이 경쟁 조건을 피하도록 설계할 것.
- 내구성(Durability): 중요한 프로젝트 지식은 git으로 추적되는 파일에 있다.
