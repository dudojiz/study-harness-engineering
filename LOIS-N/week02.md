# 명령 파일 분산

하네스의 명령 파일의 길이는 매우 중요하다. 명령 파일의 길이가 길 수록 생기는 문제는 다음과 같다

1. 명령 파일이 컨텍스트 윈도우를 많이 점유한다
2. Lost in the middle - 파일 중간에 있는 정보를 덜 활용
3. 규칙의 우선순위에 충돌이 발생한다.
4. 유지보수가 어렵다.
5. 모순이 생긴다.

## 문제점

이 내용을 자세히 살펴보면 다음과 같다.

### 컨텍스트 윈도우 점유

하나의 파일에 많은 명령이 들어있을 경우 작업을 위해서 하나의 파일을 전부 읽어와야 한다. 이러한 경우 파일을 읽어오는 것 + 파일을 분석하는 것 에 대한 비용을 사용할 뿐만 아니라, 추가 질의에 대한 비용도 사용할 수 있다. 이러면 초기 세팅하는데 컨텍스트를 사용하여 실제 작업 진행에 차질이 생길 수 있다.

### Lost in the middle

LLM은 긴 텍스트의 중간에 있는 정보를 더 효과적으로 사용하는 경향이 있다. 그래서 중요한 내용이 텍스트 가운데 존재한다면 해당 내용을 에이전트가 무시하고 명령을 실행하여 작업 성능이 낮게 나온다.

### 우선순위 충돌

파일에는 여러 명령이 있을 수 있다. 각각의 명령의 우선순위는 다를 수 있지만 파일 내부에서 직접 명시하지 않는다면 에이전트는 어떤 명령이 더 중요한지 생각하는데 리소스를 사용할것이고, 우리가 생각하는 결과와 다르게 나타날 수 있다.

### 유지보수 어려움

코드를 작성할 때 하나의 파일에 많은 코드가 들어있으면 유지보수가 어려운것처럼, 프롬프트 파일도 이와 동일하다. 딱 필요한 만큼만 나누어 관리할 것

### 명령의 모순

명령들이 추가될수록 기존의 명령어와 충돌이 되는 명령어가 추가될 수 있다. 파일이 길어지면 이 문제는 더 커질것.

## 해결방법은? 분산

하나의 파일에 많은 양의 정보를 담으면 앞서 말한것처럼 많은 문제가 발생한다. 이를 해결하기 위해서는 파일에 적절한 내용만 담으면 된다. 파일의 목적에 따라서 들어가는 내용이 조금씩 달라진다.

### 진입 파일 - AGENTS.md

AGENTS.md 파일은 에이전트가 작업을 시작할 때 처음 확인하는 파일이다. 그러므로 프로젝트 전체에 적용되는 범위의 내용만 작성한다

50~200줄 정도의 내용을 작성하고, 프로젝트 개요, 실행 명령, 전역 제약, 주제 문서 링크와 같은 내용들로 채우는것이 좋다.

### 주제 문서

주제 문서는 각 모듈에 대한 주제를 정리하는 파일이다. 해당 모듈에 대한 작업을 진행할 경우에만 읽는다. 특정 정보는 코드에 직접 배치하는것이 좋다고 한다. 모든 명령에는 출처, 적용 조건, 만료 조건을 명시하고, 오래되거나 중복되는 명령은 정리하는것이 필요하다.

또한 Lost in the middle을 해결하기 위해 중요한 명령은 파일의 제일 위 또는 아래에 위치하는것이 좋다. 

# 컨텍스트 유지

에이전트로 작업을 진행하다보면 컨텍스트가 가득 차는 경우가 생긴다. 최근의 에이전트들은 컨텍스트 윈도우의 양이 크고 다 찰 경우 압축을 통해 작업을 이어나갈 수 있다. 하지만 압축을 하는 경우 주요한 정보가 소실될 수 있어 새로운 세션에서 시작하는것이 조금 더 효과가 좋다.

실제로 codex를 사용해서 프로젝트를 진행할 때, 하나의 세션에서 컨텍스트를 압축해서 작업을 진행하는 것과, 컨텍스트가 다 찼을 때 새로운 세션에서 작업을 진행하는 것 중 후자가 더 만족도가 높았다.

이렇게 진행하는 경우 주의할 점이 하나 있는데 에이전트는 다른 세션을 참조할 수 없다는 것이다. 그래서 이어서 작업을 할 경우 이전 작업 내용을 정확하게 알려주는것이 필요했다. 물론 깃 커밋 내역으로 어떤 작업을 진행했는지 정도는 알아낼 수 있지만 정확도는 조금 떨어졌다. 이를 해결하가 위해 새로운 세션에서 작업을 진행할 경우 기존 세션에서 진행하던 작업 내용을 정리하는 작업을 추가로 진행해줬다.

## 일지 작성

내가 했던 해결 방법은 매 번 작업을 마칠때 마다 세션의 작업내용을 정리해달라고 하고, 정리된 내용은 다음 세션으로 넘겨주는 방식이었다. 이렇게 하면 어느정도는 전달이 되지만 일관성이 없고 작업 내역을 따로 정리하는것도 필요했다. 하네스에서는 이를 조금 더 체계적인 문서로 정리하는것을 권장한다. 문서 체계는 다음과 같다

1. PROGRESS.md
    
    프로젝트의 진행 상황을 정리하는 문서
    
2. DECISONS.md
    
    중요한 설계 과정과 이유를 기록한 문서
    
3. Git commit 내역
    
    원자적 작업 단위 완료 후 커밋하고, 커밋 메시지에 작업 내역 기록
    
4. init.sh
    
    세션의 시작과 끝에 해야할 작업 명시
    

이렇게 구체적으로 작업 내역을 기록해두면 연속적인 작업을 할 때 이전 작업에 대한 추론 비용이 줄어들 뿐만 아니라 나중에 리팩토링이나 에러 해결등 추가적인 작업을 진행할 때 빠르게 작업 내역을 불러올 수 있어 편하다. 

# 초기화

에이전트를 사용하여 코드를 작성하기 전, 에이전트가 현재 프로젝트에 대한 정보를 얻는 과정이 필요하다. 

프로젝트에 대한 이해가 부족한데 에이전트가 코드 작성을 시작하면 작업을 하면서 매 번 프로젝트에 대한 이해를 하는데 비용을 사용하게 된다. 그러므로 프로젝트를 시작하기 전 초기화를 통해 프로젝트 전반에 관한 이해와 관련 문서를 작성해두면 이러한 작업을 다시 진행하지 않아도 된다.

### 초기화 방법

일단 초기화는 처음 프로젝트를 시작할 때 단일 세션에서 진행한다. 

가장 처음 확인해야 할 부분은 프레임워크가 올바르게 설정되었는지 테스트를 진행하는것이다.

그 다음으로는 부트스트랩 계약 문서를 작성한다. 이 문서에는 프로젝트의 시작 명령, 현재 진행 상태, 프로젝트 구조 등을 작성한다.

다음으로 전체 프로젝트를 작업으로 나누고 순서를 부여하며, 인수 기준을 부여한다.

이렇게 초기화를 완료하면 깃 커밋을 통해 초기화를 완료했다는 내용을 저장한다.

이 때 주의해야 할 점이 두가지가 있다. 첫번째로는 빈 디렉토리가 아닌 프로젝트 템플릿 등을 사용해서 구조, 의존성 등을 미리 설치해두어 에이전트가 작업하기 쉽도록 해야한다. 이를 웜 스타트라고 부른다. 두번째로는 초기화 단계에서는 많은 코드를 작성하는게 아니라 부트스트랩 계약 조건이 충족되었는지를 확인하는것이다. 

# 2주차 공부하고 느낀 점

이번 주에 공부했던 내용들을 생각해보면 ai 에이전트를 사용하면서 불편했던 부분들을 보완하기 위해 해봤던 일들이 꽤 많았다. 실제로 프로젝트를 진행하면서 성능이 좋아지는것을 느꼈었는데, 스터디를 진행하면서 이를 조금 더 명확하고 구체화해서 구조를 작성하고, 모든 내용을 파일로 정리하는것이 필요하다고 생각이 들었다. 또한 프로젝트에 대한 명확한 구조화를 통해 작업을 지시하는게 필수적이라고 느꼈다. jira를 사용했던것처럼 업무를 단계적으로 나누고 정리하는 방법도 연습이 필요한 것 같다.
