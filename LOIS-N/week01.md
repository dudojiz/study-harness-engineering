# Week 01 학습 정리

## 하네스에 대해서 배우기 전에
최근 코드 에이전트들의 성능이 개발자를 대체할 수 있을 정도라는 수준에 이르렀다고 한다. 하지만 내가 사용하는 코드 에이전트는 그 정도의 성능이 나오는 것 같지 않다. 실제로 사용해보았을때, 어느정도는 잘 만들어주지만 내부를 까보면 엉망진창인 경우를 많이 느꼈다. 

내가 원하는대로 코드를 작성해주지 않고 에이전트가 마음대로 코드를 짜는 상황을 해결하려면 다음과 같은 사전작업이 필요하다
바로 ```AGENTS.md```와 같은 설계서를 ai에게 주는것이다. 이유는 다음과 같은데

1. 코드 에이전트가 모든 코드를 읽고 구조를 분석하는것은 불가능에 가까우며, 가능하더라도 자원(토큰, 시간 등)의 소모가 매우 크다
2. ai는 해당 세션에서만의 작업을 알고있기 때문에 이전, 이후의 작업 내용에 대해 몰라 의사결정을 하는것이 어렵다.
3. ai는 주어진 자료들을 바탕으로 결과를 낸다

특히 2, 3번 내용이 중요하다고 생각하는데, 현재의 ai는 결과를 내놓을 때 다음에 올 내용의 확률을 기반으로 코드를 생성한다. 그래서 같은 질문을 주더라도 나오는 결과가 달라지는것인데 AGENTS.md와 같은 파일을 주게 되면 이를 바탕으로 현재 작업에 대한 가이드라인을 주기 때문에 확률을 어느정도 내가 원하는 방향으로 유도할 수 있다. 만약 주지 않는다면? ai가 혼자서 판단하고 원하는 기능과 다른 기능을 만들것이다. 이러한 ai의 특성으로 인해 가이드라인이 있고 없고의 차이는 많이 크다.

## 그럼 하네스란?
앞서 얘기한 ```AGENTS.md```과 같은 파일은 프롬프트 파일이라고 부른다. 하네스는 이러한 파일들을 포함하고 있는 인프라라고 보는것이 맞다. 

하네스에는 다음과 같은 요소들이 있다
1. AGENTS.md와 같은 프로젝트 개요, 기술 스택 등이 들어있는 프롬프트 파일
2. 터미널, 파일 접근, 패키지 설치와 같은 실행 권한
3. 어떤 환경에서 실행되는지
4. 작업 상태를 이어가는 로그
5. 결과 확인을 위한 시스템 (테스트, 타입 검사, 린트 등)

이렇게 프로젝트 진행을 위한 모든 과정을 설계하고 AI에게 작업을 시키면 같은 모델이더라도 더 좋은 성능을 보여준다. 특히 5번 피드백에 관련한 내용이 가장 비용 대비 성능이 높다고 한다.

또한 프로그램이 작성될수록 프로그램의 내용이 변경되는것 처럼 하네스도 수정이 필요하다.

## 저장소에 모든 지식을 저장할 것
에이전트를 사용하는것을 떠나 사람간의 협엽을 할 때도 느꼈던 점 중 하나는, 내가 알고있는것을 다른 사람이 안다고 생각하면 안된다는 것이다. 처음 AI 에이전트를 사용할 때 작업 디렉토리만 할당해주고 작업을 시켰는데 내가 원하는 방식으로 작동을 하지 않았다. 그래서 외부에 정리한 문서를 발췌해서 입력으로 주었다. 그 결과 문서에 맞는 결과를 내었는데, 이를 세션마다 진행하니 필요한 부분을 찾고, 정리하는 시간이 많이 들었다.

이러한 문제를 해결하기 위해서는 모든 지식을 작업 디렉토리에 저장하는것이 중요하다. 최근의 에이전트는 mcp를 통해 외부 저장소와 통신을 할 수는 있지만 이는 직접 접근하는것에 비해 비용이 많이 든다. 그렇기 때문에 지식을 작업 디렉토리에 저장하되, 다음과 같은 구조를 가지는것이 좋다.

```
project/
├── AGENTS.md              # 진입점: 프로젝트 개요, 실행 명령어, HARD 제약
├── src/
│   ├── api/
│   │   ├── ARCHITECTURE.md  # API 레이어 아키텍처 결정
│   │   └── ...
│   ├── db/
│   │   ├── CONSTRAINTS.md   # 데이터베이스 작업 HARD 제약
│   │   └── ...
│   └── ...
├── PROGRESS.md             # 현재 진행 상황: 완료, 진행 중, 차단됨
└── Makefile                # 표준화된 명령어: setup, test, lint, check
```

앞서 하네스에 대해 얘기했던 5가지 내용들을 위와 같은 디렉토리 구조로 정리하면 좋은데, 프로젝트 전체적인 내용을 담은 문서는 전역으로, 각각의 기능에 대한 내용은 해당 디렉토리에 위치하는것이 중요하다. 에이전트는 문서의 위치를 찾는데도 비용이 발생하며, 문서에서도 현재 작업에 대한 정보를 찾는데도 비용을 사용한다. 그러므로 문서는 필요한 내용을 필요한 위치에 저장하는것이 매우 중요하다.

이렇게 구조를 작성했다면 에이전트의 작업을 관리하는것이 좋다. DB를 다룰 때 사용하는 트랜잭션과 동일한 개념으로 ACID 원칙을 통해 관리한다.

| DB의 ACID         | 에이전트 작업                            |
| ---------------- | ------------------------------------------ |
| Atomicity, 원자성   | 하나의 논리 작업은 하나의 단위로 끝나야 함. 실패하면 되돌릴 수 있어야 함 |
| Consistency, 일관성 | 작업 후 테스트, 린트, 빌드가 통과하는 상태여야 함              |
| Isolation, 격리성   | 여러 에이전트/브랜치/작업자가 서로 상태를 덮어쓰지 않아야 함         |
| Durability, 내구성  | 중요한 결정과 진행 상태는 세션 메모리가 아니라 git에 남아야 함      |

이렇게 정리를 하는 이유는 에이전트가 다음 세션에서 작업을 진행할 때 빠트리는 정보없이 완전한 상태로 받아 다음 작업을 진행하도록 하기 위해서이다. 이렇게 상태관리를 잘 진행한다면 에이전트에서 추측을 통한 코드 작성의 빈도가 줄어들고 완성도 높은 코드를 얻을 수 있을것이다.
