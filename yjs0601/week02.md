### Chapter 4
<명령 파일을 여러 파일로 분산>
AGENTS.md 파일의 양이 늘수록, 에이전트의 성능은 오히려 나빠진다.
컨텍스트 예산이 잠식 : 에이전트의 컨텍스트 윈도는 유한. 비대해진 md파일을 읽다가 토큰을 다 써버릴 수도 있다.
중간에서 길을 잃는다: 과도하게 채우다보면 중간에 중요한 정보를 건너뛸 수 있다.
우선순위 충돌 : 규칙마다 중요도가 다르지만, 파일안에 뒤섞여 있으면 뭐가 중요한지 모른다.
유지보수 붕괴 : 큰 파일은 유지보수 하기 어렵다.
모순이 쌓인다: 서로 다른 시점에 추가된 명령들이 서로 충돌.

컨텍스트 예산이 잠식 -> 명령 비대화(Instruction Bloat)
중간에서 길을 잃는다 -> 중간 손실 효과(Lost in the Middle Effect)
우선순위 충돌 -> 명령 신호 대 잡음비(SNR),라우팅 파일(Routing File),점진적 공개(Progressive Disclosure)
모순이 쌓인다 -> 우선순위 모호성(Priority Ambiguity)

분산하는 방법 
핵심 원칙: 자주 필요한 정보는 손에 닿는 곳에, 가끔 필요한 정보는 치워두고, 결코 쓰지 않을 정보는 버립니다.

진입 파일인 AGENTS.md는 50~200줄로 유지하며, 가장 자주 사용하는 항목만 담습니다. 프로젝트 개요(한두 문장), 첫 실행 명령(make setup && make test), 전역 하드 제약(협상 불가능한 규칙 최대 15개), 그리고 주제 문서 링크(한 줄 설명 + 적용 조건)입니다.

### Chapter 5
<세션을 넘어 컨텍스트를 살아있게 유지하라>
-에이전트가 장기작업 중에 "블랙아웃" 되는 이유와, 구조화된 상태(state) 영속화가 에이전트를 신뢰할 수 있는 일일 일지를 갖춘 장인으로 만드는 방법을 설명.

** 컨텍스트 윈도는 무한하지 않다.**
-context anxiety : 컨텍스트가 소진되고 있다고 느끼면 "조기 수렴" 행동을 보임.

-연속성 산출물
-재구축 비용
-드리프트
-컨텍스트 불안
-컴팩션 vs 리셋

** 연속성이 깨지면 어떤 일이 벌어지나 **
-이전 세션은 세가지 접근법으로 선택했는데, 이번 세션 에이전트는 불완전한 정보를 바탕으로 다시 결정을 내림 --> 어제 한것이 무용지물 됨.
-중복작업 : 에이전트가 특정 작업이 이미 완료됐는지 확인 할 수 없어 다시 함. 
-여러 세선에 걸쳐 구현 방양이 원래 요구사항에서 벗어날 수도 있음
-검증 격차 : 이전 세션의 검증 결과가 기록되지 않으면, 새 세션은 모든 검증을 다시 실행해야함. --> 따라서 매 세선마다 처음부터 진단하고, 귀중한 컨텍스트를 낭비하게 됨.

해결 법 : Handoff : 핵심 접근법: 에이전트를 건망증이 있는 뛰어난 엔지니어처럼 취급하세요. "퇴근" 전에 다음 "교대" 에이전트가 빠르게 이어받을 수 있도록 중요한 정보를 적어두어야 합니다.

도구 1: 진행 파일(PROGRESS.md). 가장 기본적인 연속성 산출물, 일지의 핵심입니다.
도구 2: 결정 로그(DECISIONS.md). 중요한 설계 결정과 이유를 기록합니다. 상세한 설계 문서가 필요하지 않습니다. "어떤 결정, 왜, 언제"만 있으면 됩니다. 일지의 메모입니다.

도구 3: Git 커밋을 체크포인트로. 각 원자적 작업 단위 완료 후 커밋합니다. 커밋 메시지는 무엇을 했고 왜 했는지를 설명해야 합니다. 이것은 무료로 자동으로 버전이 관리되는 상태 스냅샷입니다.

도구 4: init.sh 또는 하네스 초기화 흐름. AGENTS.md에 "출근"과 "퇴근" 루틴을 명시합니다.

혼합 전략: 모든 작업에 컨텍스트 리셋이 필요하지 않습니다. 짧은 작업(30분 이하)은 한 세션 내에서 완료할 수 있습니다. 긴 작업(세션에 걸쳐 있는)은 연속성을 위해 진행 파일과 결정 로그를 사용해야 합니다. 결정 기준: 작업에 윈도의 60% 이상이 필요하다면 핸드오프(handoff) 준비를 시작하세요.

핵심정리
-컨텍스트 윈도는 유한한 자원
-해결책은 더 큰 윈도가 아닌 더 나은 상태 영속화. 
진행파일+ 결정 로그 + git 체크포인트로
-에이전트를 건망증 엔지니어 취급하자. 매번 "퇴근"전에 무엇을 했는지, 왜 했는지, 다음은 무엇인지 적어놓자.
-재구축 비용이 핵심 지표
-혼합 전략

### Chapter 6
<모든 에이전트 세션전에 초기화하라>
-에이전트가 작업 시작하기전, 별도의 단계를 사용해 기본 환경을 준비,
검증 명령이 통과하도록 하고, 프로젝트 구조를 이해.

**기초와 벽 : 근본적으로 다른 두가지 작업 **
-초기화 : 이후 모든 구현의 신뢰성과 효율성을 극대화 하는 것을 최적화

핵심 개념
-초기화 단계
-부트스트랩 계약
-콜드 스타트 vs 웜 스타트 : 웜스타트 처럼 이미 갖춰진 템플릿이나 기존 프로젝트에서 시작하는 것이 훨씬 우수함.
-핸드오프 준비성:새로운 에이전트가 인계받을 수 있는 상태. 저장소 내용만으로 충분.
-첫 번째 검증까지의 시간
-다운스트림 사용성

**초기화를 올바르게 하는 방법
초기화를 전용 단계로 취급: 첫 번째 세션은 초기화만 한다. 
1. 실행 가능한 환경
2. 검증 가능한 테스트 프레임 워크.
3. 부트스트랩 계약 문서.
4. 작업 분해.
5. Git 커밋을 체크포인트로

핵심 정리
-초기화와 구현은 최적화 목표가 다름.
-초기화의 출력은 코드가 아님. 인프라임.
-부트스트랩 계약의 네 가지 조건으로 초기화를 검증.
-웜 스타트가 콜드 스타트보다 나음.
-초기화에 투자한 시간은 이후 3~4세션에서 완전히 회수. 이것은 추가 비용이 아님. 선행 투자. 기초가 견고할수록 건물이 더 빨리 올라감.
