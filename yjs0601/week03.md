### Chapter 7
### 에이전트에게 명확한 작업경계를 그어주어야 한다
-프롬프트가 지나치게 넓으면 , 에이전트는 한 가지를 먼저 끝내기보다, 여러 가지를 동시에 시작하는 경향이 있음.

### 주의력은 유한한 자원
- 에이전트의 컨텍스트(context) 용량을 C라 하고, k개의 작업을 동시에 활성화한다고 가정.
- 각 작업에는 평균 C/k의 추론 자원이 할당
-  C/k가 단일 작업을 완료하는 데 필요한 최소 임계값 아래로 떨어지면, 어느 것도 완성되지 않음.
### 핵심 개념
- 과욕(Overreach)
- 미완성(Under-finish)
- WIP 제한(Work-in-Progress Limit)
- 완료 증거(Completion Evidence)
- 범위 표면(Scope Surface)
- 완료 압력(Completion Pressure)

### 과욕과 미완성은 공생관계
- 과욕은 주의력을 희석시키고,  희석된 주의력은 미완성을 야기 --> 남겨진 반완성 코드는 시스템 복잡도를 높이고, 이는 다음 작업에서 더 큰 과욕을 불러옴.
- 동시에 너무 많은 것을 하면, 각 작업의 리드 타임 W가 불가피하게 늘어남. 
- 에이전트에게 이는 각 기능이 시작에서 검증된 완료까지 더 오래 걸리고 실패 확률이 커짐을 의미.

## 4. 검증 완료율(VCR) 모니터링
하네스는 VCR(Verified Completion Rate) = 검증된 작업 / 활성화된 작업을 지속적으로 추적해야 합니다. VCR < 1.0일 때 새 작업 활성화를 차단.

- ai는 "완료"가 무엇을 의미하는지 모른다.
--> "완료"가 무엇을 의미하는지 전혀 알려주지 않았기 때문에, 에이전트는 자신만의 기준을 사용했습니다 — "코드를 많이 작성했고 꽤 완성된 것처럼 보인다."
- 기능목록(feature list) : 하네스 세계에서 기능 목록은 인간을 위한 메모가 아닌, 전체 하네스의 근간(backbone).
- scheduler는 이것을 바탕으로 작업을 선택, verifier는 이것을 바탕으로 완료를 판단, handoff 보고기는 이것을 바탕으로 요약본을 생성.

### 에이전트는 "완료"의 의미를 모른다.
- 에이전트의 자신만의 암묵적인 "완료" 기준은 "코드에 명백한 문법 오류가 없다."
- But 내가 필요한 것은 end-to-end 동작 검증.
-  Anthropic의 엔지니어링 데이터에 따르면 좋은 진행 기록은 세션 시작 진단 시간을 60-80% 줄인다.

### 핵심 개념
- 기능 목록은 하네스 프리미티브(primitive) :"프리미티브"란 시스템에서 더 이상 분해할 수 없는 기본 구성 요소를 의미
- 삼중 구조
- 상태 기계 모델
- 패스 상태 게이팅(Pass-state gating)
- 단일 진실 원천(Single source of truth)
- 역압력(Back-pressure)

### 기능 목록이 "프리미티브"여야 하는 이유
1. 스케줄러(Scheduler): 상태를 읽고, 다음 not_started 기능을 선택. (ex.공장 생산 계획 시스템)

2. 검증기(Verifier): 검증 명령을 실행하고, 상태 전환을 허용할지 결정. (ex.품질 검사)

3. 핸드오프 보고기(Handoff reporter): 기능 목록에서 자동으로 세션 핸드오프 요약을 생성.(ex.자동 교대 근무 보고서)

4. 진행 추적기(Progress tracker): 상태 분포를 집계하고, 프로젝트 건강 지표를 제공. (ex.대시보드)

### Chapter 9
### 에이전트가 너무 일찍 완료를 선언하지 못하도록 방지하기
- 하네스(harness)는 에이전트의 "느낌"을 외부화된 실행 기반 검증(verification)으로 대체해야함.

### 미끄러운 경사면
- 정보는 모든 단계에서 손실됩니다. 작업 명세에서 코드 구현을 거쳐 런타임 동작에 이르기까지, 모든 변환은 편향을 유발할 수 있으며, 건너뛴 모든 검증은 정보 비대칭을 악화시킴.

### 핵심개념
- 조기 완료 선언(Premature Completion Declaration)
- 신뢰도 보정 편향(Confidence Calibration Bias)
- 종료 기준(Termination Criteria)
- 검증-유효성 검사 이중 게이트(Verification-Validation Dual Gate)
- 런타임 피드백 신호(Runtime Feedback Signals)
- 완료 우선순위 제약(Completion Priority Constraint)

### 단위 테스트 통과 != 작업완료
- 인터페이스 불일치
- 상태 전파 오류
- 환경 의존성

### 조기 제출을 방지하는 방법
### 1. 종료 판단 외부화
- 하네스는 런타임 신호를 입력으로 사용하여 독립적으로 종료 유효성 검사를 실행해야 하며, 에이전트의 신뢰도를 사용해서는 안 됨.
## 완료의 정의
- 기능 완료 = 엔드투엔드 검증 통과, "코드가 작성됨"이 아님
- 필요한 검증 레벨:
  1. 단위 테스트 통과
  2. 통합 테스트 통과
  3. 엔드투엔드 흐름 검증 통과
- 레벨 1이 실패하면 레벨 2로 진행하지 않습니다
- 레벨 2가 실패하면 레벨 3으로 진행하지 않습니다

### 2. 3단계 종료 유효성 검사 구축
- 레이어 1: 문법 및 정적 분석
- 레이어 2: 런타임 동작 검증
- 레이어 3: 시스템 수준 확인

### 3. 에이전트를 위한 좋은 "빨간 펜 수정" 설계
-  에이전트에 대한 오류 메시지에는 수정 지침이 포함되어야 합니다
-"테스트 실패"를 사용하지 말고, "테스트 실패: POST /api/reset-password가 500을 반환했습니다. 환경 변수에 이메일 서비스 설정이 있는지 확인하십시오. 템플릿 파일은 templates/reset-email.html에 있어야 합니다."를 사용.

### 4. 런타임 신호 수집
- 애플리케이션이 성공적으로 시작되어 준비 상태에 도달했는가?
- 핵심 기능 경로가 런타임에 성공적으로 실행되었는가?
- 데이터베이스 쓰기, 파일 작업 및 기타 부작용이 올바른가?
- 임시 리소스가 정리되었는가?

### 핵심 요점
- 에이전트는 체계적으로 과도한 자신감을 보임.
- 완료판단은 외부화되어야함.
- 3단계 유효성 검사가 모두 필수.
- 핵심 기능이 검증되기 전에는 리팩터링 하지 마라.
