# 하나의 세션에 하나의 기능만

에이전트에게 넓은 범위의 작업을 시키면 관련된 기능들을 한꺼번에 수정한다. 예를 들어 사용자 인증 기능을 만들어달라고 했을 때 회원가입만 구현하는 것이 아니라 이메일 인증, 비밀번호 암호화, 에러 처리와 같은 주변 기능까지 작업을 진행한다. 또한 처음 요청한 기능도 완성되지 않는 경우가 생길 수 있다.

이런 문제가 생기는 이유는 에이전트가 사용할 수 있는 컨텍스트와 주의력이 한정되어 있기 때문이다. 여러 기능을 동시에 작업하면 각 기능에 사용할 수 있는 자원이 줄어들고, 구현만 조금씩 된 상태에서 검증까지 진행하지 못한다. 진행 중인 작업이 많아질수록 서로 의존하는 코드도 늘어나기 때문에 다음 세션에서 작업을 이어가기도 어려워진다.

이를 해결하기 위해서는 WIP(Work in Progress)를 1로 제한하는 것이 좋다. 한 번에 하나의 기능만 작업하고, 현재 기능의 검증이 끝난 뒤에 다음 기능을 시작하도록 만드는 것이다. 에이전트가 작업 중에 리팩토링이 필요한 부분이나 다른 기능을 발견하더라도 현재 작업 범위에 포함되지 않는다면 바로 수정하지 않고 다음 작업으로 기록해야 한다.

작업을 하나로 제한하는 것만으로는 부족하다. 각 작업마다 완료되었다고 판단할 수 있는 정보도 필요하다. 코드가 작성되어 있거나 에이전트가 정상적으로 보인다고 판단하는 것은 완료의 증거가 아니다. 테스트, 타입 검사, 실제 API 요청과 같이 직접 실행할 수 있는 검증 방법을 정해야 한다.

예를 들어 회원가입 기능은 다음과 같이 정리할 수 있다.

```text
기능: 사용자가 이메일과 비밀번호로 회원가입할 수 있다.
검증: 회원가입 API에 올바른 값을 요청하면 201 응답과 사용자 정보가 반환된다.
상태: active
```

이렇게 하나의 기능을 선택하고 검증까지 통과한 후 다음 작업으로 이동하면 한번에 작성하는 코드의 양은 줄어들지만 기능은 완전하게 구현된다. 에이전트의 작업량은 수정한 파일이나 코드의 줄 수가 아니라 검증을 통과한 기능의 수로 판단하는 것이 필요하다.

# 기능 목록을 통한 작업 관리

기능 목록은 에이전트가작업을 선택하고, 완료되었다고 판단하며, 다음 세션에서 어디부터 이어갈지를 결정하는 기준이다. 지난 주에 정리한 `PROGRESS.md`보다 각 기능의 동작과 검증 방법을 더 구체적으로 작성한 형태라고 볼 수 있다.

일반적인 진행 기록에는 "회원가입 완료", "장바구니 거의 완료"와 같이 작성하는 경우가 많다. 하지만 에이전트는 "거의 완료"가 어떤 상태인지 알 수 없다. 어떤 테스트가 통과했고 무엇이 남았는지 다시 코드를 읽고 추론해야 하며, 이미 끝난 기능을 다시 수정할 수도 있다.

이 문제를 막기 위해 기능 목록의 각 항목에는 다음 세 가지 내용이 필요하다.

1. 사용자가 확인할 수 있는 동작
2. 동작을 확인하기 위한 검증 명령
3. 현재 작업 상태

작업 상태는 `not_started`, `active`, `blocked`, `passing`과 같이 제한된 값으로 관리한다. `not_started`는 아직 시작하지 않은 기능, `active`는 현재 작업 중인 기능, `blocked`는 외부 의존성 등으로 진행할 수 없는 기능, `passing`은 검증을 통과한 기능을 의미한다.

```json
{
  "id": "F03",
  "behavior": "사용자가 상품을 장바구니에 추가하면 201 응답을 받는다.",
  "verification": "장바구니 API 엔드투엔드 테스트 실행",
  "state": "active",
  "evidence": null
}
```

여기서 중요한 점은 에이전트가 자신의 판단만으로 상태를 `passing`으로 변경하면 안 된다는 것이다. 검증 명령이 성공했을 때만 하네스가 상태를 변경하도록 해야 한다. 그러면 기능 목록을 읽는 스케줄러는 다음 작업을 고를 수 있고, 검증기는 완료 여부를 판단할 수 있으며, 다음 세션은 별도의 추론 없이 현재 상태를 알 수 있다.

기능의 크기도 적절하게 정해야 한다. "쇼핑몰 만들기"처럼 하나의 세션에서 끝낼 수 없는 작업은 너무 크고, "Cart 모델에 필드 하나 추가"처럼 사용자 동작을 확인할 수 없는 작업은 너무 작다. 하나의 세션에서 구현과 검증을 모두 마칠 수 있는 사용자 동작을 기준으로 나누는 것이 좋다.

결국 기능 목록은 프로젝트에서 해야 할 일에 대한 단일 진실 원천이 된다. 대화, TODO 주석, 별도의 메모에 요구사항이 흩어져 있으면 내용이 서로 달라질 수 있다. 기능의 설명, 검증 방법, 상태를 하나의 파일에서 관리하면 에이전트가 작업 범위를 임의로 해석하는 일을 줄일 수 있다.

# 너무 이른 완료 선언 막기

에이전트는 코드를 작성하고 단위 테스트가 통과하면 작업이 완료되었다고 말하는 경우가 많다. 하지만 단위 테스트는 외부 의존성을 모킹하기 때문에 컴포넌트 사이의 연결 문제나 실제 환경의 설정 오류를 찾지 못할 수 있다. 각 코드가 따로 동작하는 것과 사용자의 전체 흐름이 정상적으로 동작하는 것은 다른 문제이다.

따라서 완료 여부는 에이전트의 자신감이 아니라 외부에서 확인할 수 있는 실행 결과로 판단해야 한다. 이를 위해 다음과 같이 세 단계로 검증할 수 있다.

1. 문법 검사, 타입 검사, 린트와 같은 정적 분석
2. 단위 테스트와 애플리케이션 실행을 통한 런타임 검증
3. 통합 테스트와 엔드투엔드 테스트를 통한 사용자 흐름 검증

앞 단계가 실패하면 다음 단계로 넘어가지 않고 문제를 먼저 수정해야 한다. 세 단계가 모두 통과했을 때만 기능을 완료 상태로 변경한다. 이 과정에서 기능 구현을 담당한 에이전트와 완료 여부를 판단하는 검증기를 분리하면 자기 작업을 긍정적으로 평가하는 문제도 줄일 수 있다.

검증 실패 결과도 단순히 "테스트 실패"라고 전달하는 것보다 어떤 요청에서 어떤 결과가 나왔는지 구체적으로 알려주는 것이 좋다. 에이전트가 원인을 찾는 데 사용할 수 있는 로그, 실패한 테스트 이름, 예상값과 실제값을 함께 제공하면 사람의 개입 없이 다시 수정하고 검증하는 흐름을 만들 수 있다.

또한 핵심 동작의 검증이 끝나기 전에 리팩토링이나 성능 개선을 시작하지 않도록 해야 한다. 코드 스타일을 정리하는 동안 아직 검증되지 않은 동작이 변경될 수 있고, 원래 기능의 완료가 더 늦어질 수 있기 때문이다. 기능 동작 확인, 성능 개선, 코드 정리 순서로 우선순위를 정하는 것이 필요하다.

# 3주차 공부하고 느낀 점

이번 주 내용은 에이전트에게 작업을 많이 시키는 것보다 하나의 기능을 정확히 완료하게 만드는 방법에 대한 내용이었다. 지금까지 에이전트가 많은 파일을 수정하면 일을 많이 했다고 생각했던 경우가 있었는데, 실제 기준은 동작하는 기능과 검증 결과가 되어야 한다는 점이 중요하게 느껴졌다.

특히 기능 목록에 동작, 검증 방법, 상태를 같이 작성하는 방식은 개발 업무를 이슈로 나누는 것과 비슷하지만 에이전트가 직접 읽고 다음 행동을 결정한다는 차이가 있다. 단순히 계획을 정리하는 문서가 아니라 작업 선택과 완료 판단에 사용되는 데이터라는 점을 생각하면서 작성해봐야겠다.
