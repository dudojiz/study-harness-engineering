### Chapter 10
## 엔드투엔드 테스트 만이 진정한 검증이다.
- 단위 테스트의 맹점
단위 테스트의 설계 철학은 격리이다. 의존성을 모킹하고 테스트 대상 단위에만 집중하는 것.
이 철학이 단위 테스트를 빠르고 정밀하게 만들지만, 동시에 체계적인 맹점을 만들어 냄.
- 인터페이스 불일치 : 렌더 프로세스가 프리로드 스크립트에 전달하는 파일 경로는 상대 경로이지만, 프로드 스크립트는 절대 경로를 기대함.
- 상태 전파 오류 : 데이터베이스 마이그레이션이 테이블 스키마를 변경했지만, ORM 캐싱 계층은 여전히 이전 스키마에 대한 캐시 항목을 보유하고 있음. 
단위 테스트는 매번 완전히 새로운 모킹환경을 제공하므로, 이러한 계층 간 불일치를 드러내지 않음.
- 리소스 수명 주기 문제 : 파일핸들, 데이터베이스 연결, 네트워크 소켓의 획득 및 해제는 여러 컴포넌트에 걸쳐 있음. 단위 테스트는 각 테스트를 위해 독립적인 리소스를 생성하고 소멸시키므로, 리소스 경험이나 누수를 드러내지 못함.
- 환경 의존성 : 코드는 테스트 환경(모든 것이 모킹된 곳)에서는 올바르게 동작하지만, 설정 차이, 네트워크 지연, 또는 서비스 불가용성으로 인해 실제 환경에서는 실패합니다. 

## 엔드투엔드 테스트는 결과만 바꾸는 것이 아니라 행동을 바꾼다
1. 컴포넌트 상호작용 고려 : 코드를 작성하면서 "이 인터페이스가 업스트림과 어떻게 연결되는가"를 생각하게 됨. 단순히 하나의 함수에만 집중하지 않는다.
2. 아키텍처 경계 준수 : 아키텍처 제약이 있는 시스템에서 엔드투엔드 테스트는 에이전트가 경계 규칙을 준수하도록 강제함.
3. 오류 경로 처리 : 엔드투엔드 테스트는 보통 실패 시나리오를 포함하므로, 에이전트가 예외 처리를 고려하게 만듦.

### 핵심 개념
- 리뷰 피드백 승격 :반복되는 코드 리뷰 코멘트를 자동화된 테스트로 전환합니다. 반복되는 문제가 발견될 때마다 규칙을 추가하면, 하네스(harness)가 자동으로 강화됨. 
- 에이전트 지향 오류 메시지 : 실패 메시지는 단순히 "무엇이 잘못됐는지"를 명시해서는 안 되고, 에이전트에게 정확히 어떻게 수정하는지도 알려줘야 함. 이것이 테스트 실패를 자기 수정 피드백 루프로 만듦.

### Chapter 11
### 에이전트의 런타임을 관측 가능하게 만들어라
### 핵심 개념
- 런타임 관측 가능성 :로그, 트레이스(trace), 프로세스 이벤트, 상태 확인 등 시스템 수준의 신호입니다.
- 프로세스 관측 가능성 :계획, 채점 루브릭(rubric), 인수 기준 등 하네스 결정 산출물에 대한 가시성입니다.
- 태스크 트레이스 : 태스크 시작부터 완료까지의 완전한 결정 경로 기록입니다. 
- 스프린트 계약 : 코딩 시작 전에 협상되는 단기 합의입니다. 
- 평가자 루브릭 : 품질 평가를 주관적 판단에서 증거 기반 구조화된 채점으로 변환합니다. 
- 계층화된 관측 가능성 

### 왜 이런 일이 발생하는 가
## 관측 가능성 부재의 실제 비용
- "정확함"과 "정확해 보임"을 구별할 수 없다: 코드 리뷰 중에 함수가 완벽하게 보입니다—올바른 구문, 탄탄한 로직. 그러나 런타임에서 엣지 케이스 처리 오류가 특정 입력에서 잘못된 결과를 만들어낸다.
- 평가가 신비주의가 된다: 채점 루브릭과 인수 기준 없이는 평가자(사람 또는 에이전트)가 암묵적 가정에 의존합니다. 동일한 출력이 서로 다른 평가자로부터 완전히 다른 평가를 받을 수 있다.
- 재시도가 맹목적인 추측이 된다: 에이전트가 왜 실패했는지 모르면, 재시도 방향이 무작위입니다. 실제 실패 근본 원인을 무시하고 관련 없는 코드 경로를 고치면서 잘못된 방향으로 반복적으로 시도할 수 있다.
- 세션 핸드오프(handoff) 정보 절벽: 완료되지 않은 작업이 다음 세션으로 인계될 때, 관측 가능성 부재는 새 세션이 시스템 상태를 처음부터 진단해야 함을 의미한다.

### 올바르게 하는 방법
1. . 런타임 신호 수집을 하네스에 구축하라
- 애플리케이션 수명 주기: 시작, 준비, 실행, 종료 단계 상태
- 기능 경로 실행: 진입점, 체크포인트, 종료를 포함한 중요 경로 실행 기록
- 데이터 흐름: 컴포넌트 간 데이터 흐름 기록
- 리소스 활용: 비정상적인 리소스 사용 패턴 (예: 지속적으로 증가하는 메모리)
- 오류 및 예외: 오류 메시지만이 아닌 전체 오류 컨텍스트

2. 스프린트 계약을 구현하라 : 각 작업 시작 전에, 생성자와 평가자(동일한 에이전트의 서로 다른 호출일 수 있음)가 계약을 협상합니다.
3. 평가자 루브릭을 수립하라: "좋은가 아닌가"를 정량화 가능한 채점으로 전환합니다.
4. OpenTelemetry로 표준화하라 : 각 하네스 세션에 대한 트레이스(trace)를, 각 작업에 대한 스팬(span)을, 각 검증 단계에 대한 하위 스팬을 생성하세요.


### Chapter 12
### 모든 세션은 클린 상태(clean state)로 끝나야 한다
## 핵심 개념
- 클린 상태(Clean state): 세션 종료 시 시스템이 다섯 가지 조건을 만족하는 것입니다—빌드 통과, 테스트 통과, 진행 상황 기록됨, 오래된 산출물 없음, 시작 경로 사용 가능
- 세션 무결성(Session integrity): 데이터베이스 트랜잭션과 유사합니다—완전히 커밋하고 클린 상태를 남기거나, 마지막 일관된 상태로 롤백.
- 품질 문서(Quality document): 각 모듈의 품질 등급을 지속적으로 기록하는 활성 산출물
- 클린업 루프(Cleanup loop): 코드베이스의 엔트로피(entropy)를 체계적으로 줄이기 위한 정기적인 유지보수 세션임.
- 하네스 단순화(Harness simplification): 모델 역량이 향상됨에 따라, 더 이상 필요하지 않은 하네스 구성 요소를 주기적으로 제거.
- 멱등 정리(Idempotent cleanup): 정리 작업이 몇 번 실행되든 동일한 결과를 생성합니다. 

### 핵심 정리
- 클린 상태는 세션 완료의 필요 조건입니다—선택적 정리 작업이 아니라, "완료의 정의"의 일부입니다.
- 다섯 가지 차원 모두 필요합니다—빌드, 테스트, 진행 상황, 산출물, 시작—각각 명시적으로 검사되어야 합니다.
- 품질 문서는 코드베이스 건강을 추적 가능하게 만듭니다—저하되고 있다는 것을 알아야만 수정할 수 있습니다.
- 주기적으로 하네스를 단순화하세요—모델 역량이 향상됨에 따라, 더 이상 필요 없는 제약을 제거하세요.
- "나중에 정리"는 절대 정리하지 않는다는 의미입니다—엔트로피 증가가 기본 상태이며, 능동적인 정리만이 이를 막을 수 있습니다.

### 수동 프롬프팅에서 자율 루프로
- /goal: 가장 단순한 루프 :"모든 테스트 통과, 린트 경고 제로, main에 병합"
--> 1단계: 수동으로 하나씩 프롬프팅.
--> 2단계: 여러 단계가 포함된 긴 프롬프트.
--> 3단계: 에이전트 자기 성찰과 자기 주도.
--> 4단계: 독립적인 중단 판단 
끝이 있다 → /goal
끝이 없고 계속 지켜봐야 함 → /loop
